2    # This is the "master security properties file".
3    #
4    # An alternate java.security properties file may be specified
5    # from the command line via the system property
6    #
7    #    -Djava.security.properties=<URL>
8    #
9    # This properties file appends to the master security properties file.
10   # If both properties files specify values for the same key, the value
11   # from the command-line properties file is selected, as it is the last
12   # one loaded.
13   #
14   # Also, if you specify
15   #
16   #    -Djava.security.properties==<URL> (2 equals),
17   #
18   # then that properties file completely overrides the master security
19   # properties file.
20   #
21   # To disable the ability to specify an additional properties file from
22   # the command line, set the key security.overridePropertiesFile
23   # to false in the master security properties file. It is set to true
24   # by default.
25   #
26   # If this properties file fails to load, the JDK implementation will throw
27   # an unspecified error when initializing the java.security.Security class.
28   # Properties in this file are typically parsed only once. If any of the
29   # properties are modified, applications should be restarted to ensure the
30   # changes are properly reflected.
31   #
32   # The special "include" property can be defined one or multiple times with
33   # a filesystem path value. The effect of each definition is to include a
34   # referred security properties file inline, adding all its properties.
35   # Security properties defined before an include statement may be overridden
36   # by properties in the included file, if their names match. Conversely,
37   # properties defined after an include statement may override properties in
38   # the included file.
39   #
40   # Included files, as well as files pointed to by java.security.properties,
41   # can include other files recursively. Paths may be absolute or relative.
42   # Each relative path is resolved against the base file containing its
43   # "include" definition, if local. Paths may contain system properties for
44   # expansion in the form of ${system.property}. If a system property does
45   # not have a value, it expands to the empty string.
46   #
47   # An error will be thrown if a file cannot be included. This may happen
48   # if the file cannot be resolved, does not exist, is a directory, there are
49   # insufficient permissions to read it, it is recursively included more than
50   # once, or for any other reason. For a secure JDK configuration, it is
51   # important to review OS write permissions assigned to any file included.
52   #
53   # Examples:
54   #   1) include ${java.home}/conf/security/extra.security
55   #   2) include extra.security
56   #   3) include ${java.home}/conf/security/profile${SecurityProfile}.security
57   #

59   # In this file, various security properties are set for use by
60   # java.security classes. This is where users can statically register
61   # Cryptography Package Providers ("providers" for short). The term
62   # "provider" refers to a package or set of packages that supply a
63   # concrete implementation of a subset of the cryptography aspects of
64   # the Java Security API. A provider may, for example, implement one or
65   # more digital signature algorithms or message digest algorithms.
66   #
67   # Each provider must implement a subclass of the Provider class.
68   # To register a provider in this master security properties file,
69   # specify the provider and priority in the format
70   #
71   #    security.provider.<n>=<provName | className>
72   #
73   # This declares a provider, and specifies its preference
74   # order n. The preference order is the order in which providers are
75   # searched for requested algorithms (when no specific provider is
76   # requested). The order is 1-based; 1 is the most preferred, followed
77   # by 2, and so on.
78   #
79   # <provName> must specify the name of the Provider as passed to its super
80   # class java.security.Provider constructor. This is for providers loaded
81   # through the ServiceLoader mechanism.
82   #
83   # <className> must specify the subclass of the Provider class whose
84   # constructor sets the values of various properties that are required
85   # for the Java Security API to look up the algorithms or other
86   # facilities implemented by the provider. This is for providers loaded
87   # through classpath.
88   #
89   # Note: Providers can be dynamically registered instead by calls to
90   # either the addProvider or insertProviderAt method in the Security
91   # class.
92

94   # List of providers and their preference orders (see above):
95   #

97   security.provider.2=SunRsaSign

200  #
201  # NIST SP 800-90Ar1 lists several DRBG mechanisms. Each can be configured
202  # with a DRBG algorithm name, and can be instantiated with a security strength,

204  # and the default instantiation request of "DRBG" SecureRandom implementations

212  # Please note that the SUN implementation of DRBG always supports reseeding.
213  #
214  # The value of this property is a comma-separated list of all configurable
215  # aspects. The aspects can appear in any order but the same aspect can only
216  # appear at most once. Its BNF-style definition is:
217  #
218  #   Value:
219  #     aspect { "," aspect }
220  #
221  #   aspect:
222  #     mech_name | algorithm_name | strength | capability | df
223  #

225  #   mech_name:

229  #   // HMAC_DRBG, default "SHA-256". The "AES-***" names are for CTR_DRBG,

231  #   // when using the unlimited.
232  #   algorithm_name:

234  #     "SHA-512/256" | "SHA-384" | "SHA-512" |
235  #     "AES-128" | "AES-192" | "AES-256"

490  # Algorithm restrictions for certification path (CertPath) processing
491  #
492  # In some environments, certain algorithms or key lengths may be undesirable
493  # for certification path building and validation.  For example, "MD2" is
494  # generally no longer considered to be a secure hash algorithm.  This section
495  # describes the mechanism for disabling algorithms based on algorithm name
496  # and/or key length.  This includes algorithms used in certificates, as well
497  # as revocation information such as CRLs and signed OCSP Responses.
498  # The syntax of the disabled algorithm string is described as follows:
499  #   DisabledAlgorithms:
500  #       " DisabledAlgorithm { , DisabledAlgorithm } "
501  #
502  #   DisabledAlgorithm:
503  #       AlgorithmName [Constraint] { '&' Constraint } | IncludeProperty
504  #
505  #   AlgorithmName:
506  #       (see below)
507  #
508  #   Constraint:
509  #       KeySizeConstraint | CAConstraint | DenyAfterConstraint |
510  #       UsageConstraint
511  #
512  #   KeySizeConstraint:
513  #       keySize Operator KeyLength
514  #
515  #   Operator:
516  #       <= | < | == | != | >= | >
517  #
518  #   KeyLength:
519  #       Integer value of the algorithm's key length in bits
520  #
521  #   CAConstraint:
522  #       jdkCA
523  #
524  #   DenyAfterConstraint:
525  #       denyAfter YYYY-MM-DD
526  #
527  #   UsageConstraint:
528  #       usage UsageType { UsageType }
529  #
530  #   UsageType:
531  #       TLSServer | TLSClient | SignedJAR
532  #
533  #   IncludeProperty:
534  #       include <security property>
535  #
536  # The "AlgorithmName" is the standard algorithm name of the disabled
537  # algorithm. See the Java Security Standard Algorithm Names Specification
538  # for information about Standard Algorithm Names.  Matching is
539  # performed using a case-insensitive sub-element matching rule.  (For
540  # example, in "SHA1withECDSA" the sub-elements are "SHA1" for hashing and
541  # "ECDSA" for signatures.)  If the assertion "AlgorithmName" is a
542  # sub-element of the certificate algorithm name, the algorithm will be
543  # rejected during certification path building and validation.  For example,
544  # the assertion algorithm name "DSA" will disable all certificate algorithms
545  # that rely on DSA, such as NONEwithDSA, SHA1withDSA.  However, the assertion
546  # will not disable algorithms related to "ECDSA".
547  #
548  # The "IncludeProperty" allows a implementation-defined security property that
549  # can be included in the disabledAlgorithms properties.  These properties are
550  # to help manage common actions easier across multiple disabledAlgorithm
551  # properties.
552  # There is one defined security property:  jdk.disabled.namedCurves
553  # See the property for more specific details.
554  #
555  #
556  # A "Constraint" defines restrictions on the keys and/or certificates for
557  # a specified AlgorithmName:
558  #
559  #   KeySizeConstraint:
560  #     keySize Operator KeyLength
561  #       The constraint requires a key of a valid size range if the
562  #       "AlgorithmName" is of a key algorithm.  The "KeyLength" indicates
563  #       the key size specified in number of bits.  For example,
564  #       "RSA keySize <= 1024" indicates that any RSA key with key size less
565  #       than or equal to 1024 bits should be disabled, and
566  #       "RSA keySize < 1024, RSA keySize > 2048" indicates that any RSA key
567  #       with key size less than 1024 or greater than 2048 should be disabled.
568  #       This constraint is only used on algorithms that have a key size.
569  #
570  #   CAConstraint:
571  #     jdkCA
572  #       This constraint prohibits the specified algorithm only if the
573  #       algorithm is used in a certificate chain that terminates at a marked
574  #       trust anchor in the lib/security/cacerts keystore.  If the jdkCA
575  #       constraint is not set, then all chains using the specified algorithm
576  #       are restricted.  jdkCA may only be used once in a DisabledAlgorithm
577  #       expression.
578  #       Example:  To apply this constraint to SHA-1 certificates, include
579  #       the following:  "SHA1 jdkCA"
580  #
581  #   DenyAfterConstraint:
582  #     denyAfter YYYY-MM-DD
583  #       This constraint prohibits a certificate with the specified algorithm
584  #       from being used after the date regardless of the certificate's
585  #       validity.  JAR files that are signed and timestamped before the
586  #       constraint date with certificates containing the disabled algorithm
587  #       will not be restricted.  The date is processed in the UTC timezone.
588  #       This constraint can only be used once in a DisabledAlgorithm
589  #       expression.
590  #       Example:  To deny usage of RSA 2048 bit certificates after Feb 3 2020,
